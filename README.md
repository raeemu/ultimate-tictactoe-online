# ultimate-tictactoe-online

Веб-приложение для онлайн-игры Ultimate Tic-Tac-Toe в режиме 1v1.

Проект состоит из React frontend и NestJS backend. Backend отвечает за авторизацию, матчмейкинг, WebSocket-матчи, игровую логику, профиль пользователя, историю матчей, рейтинг и работу с базой данных.

## Структура проекта

```text
frontend/  клиентское React-приложение
server/    backend API, WebSocket, Prisma и работа с базой данных
```

## Стек

### Frontend

- React 19 для пользовательского интерфейса.
- React Router для страниц `/auth`, `/register`, `/lobby`, `/profile`, `/rules`, `/game/:matchId`.
- Vite для dev-сервера и production-сборки.
- Socket.IO Client для онлайн-матчей.
- Fetch API для HTTP-запросов к backend.
- CSS без UI-фреймворка.
- JWT access token хранится в `localStorage` и используется для восстановления сессии после перезагрузки страницы.

### Backend

- NestJS для HTTP API и модульной структуры приложения.
- Socket.IO через NestJS WebSocket Gateway для онлайн-матчей.
- Prisma ORM для работы с базой данных.
- PostgreSQL как основная база данных.
- Redis для очереди матчмейкинга.
- JWT + Passport для авторизации.
- bcrypt для хэширования паролей.
- class-validator / class-transformer для валидации DTO.
- Jest для unit- и e2e-тестов.

## Текущий функционал

### Авторизация

- Регистрация пользователя по `username`, `email` и `password`.
- Вход по логину и паролю.
- Получение текущего пользователя через `GET /auth/me`.
- Хранение access token на клиенте.
- Автоматическое восстановление сессии после перезагрузки страницы.
- Выход из аккаунта на клиенте.
- Защита приватных страниц от неавторизованных пользователей.

### Маршрутизация frontend

- `/auth` - вход.
- `/register` - регистрация.
- `/lobby` - лобби и поиск игры.
- `/profile` - профиль пользователя, статистика и история матчей.
- `/rules` - страница с правилами Ultimate Tic-Tac-Toe.
- `/game/:matchId` - игровая страница конкретного матча.
- Неизвестные маршруты перенаправляются на `/lobby` или `/auth` в зависимости от состояния авторизации.

### Лобби и матчмейкинг

- Авторизованный пользователь может встать в очередь поиска игры.
- Пользователь может выйти из очереди.
- Backend подбирает двух игроков и создает матч.
- Первый игрок в очереди получает символ `X`.
- Второй найденный игрок получает символ `O`.
- Frontend отслеживает состояние очереди и найденный матч.
- После нахождения пары пользователь может перейти на страницу игры.

### Игровой процесс

- Поддерживается Ultimate Tic-Tac-Toe с полем 9x9, разделенным на 9 локальных досок.
- Backend хранит состояние матча, доску, macroboard, активную локальную доску и текущий ход.
- Backend проверяет корректность каждого хода.
- Игрок может ходить только своим символом и только в свой ход.
- Backend определяет победу, ничью и продолжение партии.
- Состояние матча синхронизируется между игроками через WebSocket.
- На frontend отображаются игровая доска, текущий статус партии и результат завершения.

### WebSocket

WebSocket namespace:

```text
/matches
```

События:

```text
match:join     подключение к комнате матча
match:move     отправка хода
match:abandon  выход из матча
```

Backend отправляет обновленное состояние матча участникам комнаты после ходов и выхода из матча.

### Завершение и выход из матча

- Матч может завершиться победой.
- Матч может завершиться ничьей.
- Игрок может покинуть активный матч после подтверждения.
- При выходе матч получает статус `ABANDONED`.
- Backend сохраняет, кто именно покинул матч, в поле `abandonedById`.
- Покинувший игрок получает поражение.
- Соперник покинувшего игрока получает победу.

### Рейтинг

- Начальный рейтинг пользователя задается в базе данных.
- За победу начисляется `+25` рейтинга.
- За поражение списывается `-25` рейтинга.
- При ничьей рейтинг не изменяется.
- При выходе из матча покинувший игрок получает `-25`, соперник получает `+25`.
- Изменение рейтинга отображается в истории матчей.

### Профиль пользователя

На странице профиля отображаются:

- имя пользователя;
- email;
- дата регистрации;
- текущий рейтинг;
- количество матчей;
- количество побед;
- количество поражений;
- количество ничьих;
- количество матчей, которые пользователь сам покинул;
- история матчей.

### История матчей

- История показывает последние 20 матчей пользователя.
- Есть кнопка `Показать больше`, которая загружает следующие 20 матчей.
- Для каждого матча отображается:
  - результат;
  - соперник;
  - символ пользователя `X` или `O`;
  - изменение рейтинга;
  - количество ходов;
  - дата матча;
  - ссылка продолжения для активных матчей.

## Backend API

### Auth

```text
POST /auth/register  регистрация пользователя
POST /auth/login     вход пользователя
GET  /auth/me        текущий пользователь
```

### Matchmaking

```text
GET    /matchmaking/queue  состояние очереди пользователя
POST   /matchmaking/queue  войти в очередь
DELETE /matchmaking/queue  выйти из очереди
```

### Matches

```text
POST /matches/:matchId/moves  сделать ход в матче
```

Основной realtime-обмен по матчу выполняется через WebSocket namespace `/matches`.

### Profile

```text
GET /profile/me
```

Query parameters:

```text
offset  смещение истории матчей для дозагрузки
```

Пример:

```text
GET /profile/me?offset=20
```

## База данных

База данных описана через Prisma schema.

Основные модели:

- `User` - пользователь, авторизационные данные, рейтинг.
- `Match` - матч, игроки, статус, состояние поля, победитель, покинувший игрок.
- `Move` - ход пользователя в матче.

Основные enum:

- `MatchStatus`: `WAITING`, `ACTIVE`, `FINISHED`, `ABANDONED`.
- `CellValue`: `X`, `O`.

Миграции Prisma хранятся в `server/prisma/migrations` и должны попадать в git, потому что они фиксируют историю изменений структуры базы данных.

## Переменные окружения backend

В каталоге `server` нужен `.env` с настройками подключения к базе данных, Redis и JWT.

Пример:

```env
DATABASE_URL="postgresql://USER:PASSWORD@localhost:5432/DATABASE"
REDIS_URL="redis://localhost:6379"
JWT_SECRET="REPLACE_WITH_SECRET"
```

Конкретные значения зависят от локального окружения и не должны попадать в git.

## Запуск в режиме разработки

1. Запустить PostgreSQL и Redis.

2. Применить Prisma-миграции.

```bash
cd server
npx prisma migrate dev
```

3. При необходимости пересобрать Prisma Client.

```bash
cd server
npx prisma generate
```

4. Запустить backend.

```bash
cd server
npm run start:dev
```

Backend по умолчанию слушает `http://localhost:3000`.

5. Запустить frontend.

```bash
cd frontend
npm run dev
```

Vite dev-сервер запускает клиентское приложение и проксирует API/WebSocket-запросы на backend.

## Production-сборка

## Проверка работоспособности

Минимальный сценарий ручной проверки:

1. Зарегистрировать двух пользователей в разных браузерах или профилях браузера.
2. Войти под обоими пользователями.
3. Открыть `/rules` и проверить доступность страницы с правилами.
4. На странице `/lobby` запустить поиск игры у обоих пользователей.
5. Дождаться создания матча.
6. Перейти на страницу игры у обоих пользователей.
7. Сделать несколько ходов и проверить синхронизацию доски.
8. Завершить матч победой или покинуть матч одним из игроков.
9. Проверить изменение рейтинга и историю матчей на странице `/profile`.
10. Нажать `Показать больше`, если у пользователя больше 20 матчей.
